# 공개 CAD 생성과 별도 CLI 풀이 시험

## 개선 목적과 현재 범위

Linux 공개 API의 CPU 요청과 실제 행렬 코어 수가 달라, 문서화된 세션 전용 `-batchoptions` 경로를 검증하는 선택형 시험 모듈을 추가했습니다. 기본 `simulate`/`run_one_case`의 Analyze 동작은 유지합니다. 현재 모듈은 진단용이며 학습 데이터나 생산 프로파일을 승인하지 않습니다.

`src/pyaedt_motor/public_batch_pilot.py`는 다음 순서로 실행합니다.

1. 공개 생성기의 `--setup-only --prepare-batch-reports --keep-projects`에 해당하는 경로로 새 CAD와 보고서를 생성합니다.
2. 빌드 Native의 실제 소유권·종료·Python client 정리와 Analyze 미실행을 확인합니다.
3. 실제 예약이 있는 solve 모드에서만 별도 소유권 헬퍼로 CLI를 한 번 실행합니다. 빌드 PID와 풀이 PID는 구분합니다.
4. 알려진 정상 종료 뒤에 원시 CSV와 Native 프로파일을 읽어 10개 출력·시간 격자·코어 사용을 검사합니다.

불확실 종료에서는 Native에 다시 접속하거나 재시도하지 않습니다. CLI 결과를 기존 SDK Analyze-return 기록으로 위장하지 않습니다. 공유 레지스트리 변경과 TDM/MDD 설정을 병렬 처리의 우회책으로 사용하지 않습니다.

## 입력과 실행

Linux/Ansys2025.2·검토한 23파일 라이브러리·full360/Sym1·4CPU·새 출력 폴더를 대상으로 합니다. 계약에는 소스·라이브러리·시스템 재료·설치 바인딩·케이스의 크기/SHA가 필요합니다. 실제 호스트와 Slurm 노드를 각각 확인합니다. solve 예약은 승인 여부·시도 번호·케이스 SHA·예약 참조를 제외한 계약 전체 SHA에 결합합니다.

설치된 벤더 실행기의 심볼릭 링크는 V6 설치 검증기가 링크 연결과 대상 위치를 확인한 후 실제 파일의 크기/SHA를 검사합니다. 종료 후에도 전체 설치 검증을 반복합니다. 소스·케이스·계약 파일의 심볼릭 링크는 허용하지 않습니다.

```text
python -m pyaedt_motor execute-owned-cli --contract ABS.json --contract-sha256 SHA --output-root NEW_ABS
```

프로젝트 패키지를 설치한 환경의 모듈 진입점입니다. 패키지 내부 파일을 `python -I 파일.py`로 직접 실행하면 상대 import가 성립하지 않습니다. 클러스터의 고정 소스 실행은 별도 publication driver의 검증된 패키지 bootstrap을 사용합니다. 기본은 입력 검증만 하는 dry 모드입니다. 별도 `--execute`가 있어야 계약의 `setup_only` 또는 `solve`를 수행합니다. 설정 전용 모드는 FEA 예약과 풀이를 만들지 않습니다. 초기 진단은 보정 ID를 비워 두고 숫자 좌표 원점의 근거를 별도 보관합니다. 과거 생성기의 보정 ID를 새 생성기 보정으로 재사용하지 않습니다.

## 결과 해석과 남은 작업

원시 과학 트리·전체 ReportSetup·실제 보고서/관리자·재료·변수의 변경을 따로 기록합니다. 버전 ID·형상 캐시·표면 속성을 자동으로 무시하지 않습니다. 저장본 차이가 미해결이면 원시 지표를 보존하고 `solved_saved_closure_unproven`으로 구분합니다. 이 상태는 수치 정확도 실패나 생산 합격과 같지 않습니다.

`public_cli_retained_inputs_v1`은 실행 전후 검토에 필요한 입력을 추가 보존합니다. 빌드 세션 종료 후 미해석 AEDT를 `prepared_unsolved.aedt`로 복사하고 그 복사본에서 설정을 파싱합니다. 설치 파일·링크의 전체 관측을 전후 JSON으로 남기며, 실제 `options.txt`의 크기/SHA와 미해석 원본·설치 관측을 CLI 실행 의도에 연결합니다. 실행 직전과 종료 후 같은 기록을 재검사합니다. 이 파일 보존은 추가 Native 세션이나 풀이를 만들지 않습니다.

실제 설정 전용 실행과 같은 조건의 3/6주기 풀이를 수행했습니다. [실제 비교](experiments/2026-11-01_public_cycles/README.md)에서 기존 10개 민감도 기준은 통과했지만, 저장 상태 동등성·여러 형상과 운전점의 공간/시간 수렴 및 정식 데이터 수집·승인 연결은 남아 있습니다. 기존 두 작업의 실패 상태와 학습 미승인을 유지합니다. 효율과 출력의 정의는 [출력 범위](MOTOR_OUTPUT_DEFINITIONS.md)를 따릅니다.

`execution_evidence.solver_context`는 SDK 기본 경로를 기존 검사에 그대로 위임하고, 명시된 owned CLI 경로는 원시 인덱스·계약·별도 builder/solver 소유권·전체 CSV와 실제 profile을 재검증합니다. 실제100987에서 두 원본을 재현했습니다. 현재 이 검증기만으로 학습을 승인하지 않으며, 저장 전후 입력 동등성·좌표계·수렴 프로파일의 연결이 남아 있습니다. 포터블 회귀 fixture의 수치는 실측자료이고 OS 문맥은 명시적인 모의자료입니다.

## 2026-11-01 생산 연결 통합 검증

- **문제:** 별도 CLI 풀이를 SDK Analyze 반환처럼 취급할 수 없었고, 자료를 이동하면 검증기가 원래 실행 경로를 다시 읽었습니다. 선택 프로파일의 내부 참조도 원래 경로에 남았습니다. 초기 후보에서는 모델 생성 후 예측 시 증거 변조 검사가 빠졌습니다.
- **시도:** 명시적 생산 계약·실제 원장/영수증·소유권·전체 저장 입력 동등성·좌표계·수렴 프로파일을 연결하는 별도 검증 경로를 추가했습니다. 원시 바이트와 원래 상태를 보존하는 portable index와 선택 프로파일 wrapper를 만들고, 보관된 수치는 격리 Python의 원래 모듈 import로 다시 계산합니다. 과거 실패 진단은 학습 자료로 승격하지 않습니다.
- **확인:** 최종 후보 96개 및 독립 검토를 거친 뒤, 실제 Git index에서 추출한 642파일로 집중16개와 관련191개 검사가 통과했습니다. 원래 실행 자료를 옮기고 원래 경로를 삭제한 뒤 검증·학습 입력 판정·모델 문맥·공개 optimize CLI의 선택 프로파일 재검증을 확인했습니다. 실제 수치 파일과 명시적인 모의 권한/OS·해석식 모델을 사용한 검사이며, 실제 모델 학습 성능이나 두 속도 합격 증거는 아닙니다. 한 속도만 지원하는 시험 모델은 실행 가능한 FEA 행을 만들지 않습니다.
- **검색 비용:** 전체 증거를 매 예측마다 읽던 경로에 실행 스레드/비동기 작업 소유권을 가진 검색 세션을 추가했습니다. 시작·종료 시 전체 바이트를 검사하고 내부에는 메모리 문맥 검사를 적용합니다. 독립 측정의 12회 예측은 읽기47,484→2,680회, 내부 반복 읽기0회였습니다. 독립 predict/build는 전체 검사를 유지하며, 스레드·비동기 복사·세션 종료·예외·변조를 검사했습니다. FEA 계산시간 단축 실적과 구분합니다.
- **남은 실제 검증:** 최종 검증기 기반 FS 재검증101007, 다른 형상·속도의 수렴, 새 생산 소스의 실제 실행 및 학습 자료 승인이 필요합니다. 이전 private 검증기의 실제 FS101004 통과를 새 버전의 승인으로 재표기하지 않습니다. 계정 GPFS 여유4.1GB가 FEA 신규 투입 기준10GB보다 작아 새 작업 배치가 제한되고 있습니다. 파일 전용 점검은 Native 없는 standard CPU 작업으로 분리했으며, 실제 FEA의 저장공간 기준은 유지합니다.
